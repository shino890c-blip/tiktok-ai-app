# note（note.com）非公式API 深掘り調査レポート

> 本レポートは `planning/note-integration-design.md`（先行調査・設計書）の結論を前提に、非公式APIエンドポイント・認証フロー・実装アプローチをさらに深掘りした技術検証資料である。
> 調査方法：DevTools解析を実機で行った複数の技術記事・個人開発者による一次情報（2026年時点の観測）を収集・突き合わせ。note社が公式に保証する情報ではない点に留意。

---

## 0. 調査結論の要約

| 項目 | 結論 |
|---|---|
| 非公式APIの実在性 | `note.com/api/v1〜v3`配下に記事CRUD・画像アップロード・マガジン・ハッシュタグ等、多数の非公式内部APIが存在し、実際に動作する実装例が複数確認された |
| 認証方式 | `POST /api/v1/sessions/sign_in`（メール+パスワード）でCookie（`_note_session_v5`）発行。**2026年5月下旬よりreCAPTCHA v3が必須化**され、プログラムからの直接ログインは実質的に不可能になった |
| 記事投稿の核心API | 下書き作成`POST /api/v1/text_notes` → 下書き保存`POST /api/v1/text_notes/draft_save?id=` → 公開`PUT /api/v1/text_notes/{id}`（**フルペイロード必須・差分更新不可**） |
| 最大の実装リスク | (1) reCAPTCHA v3によるプログラム的ログイン遮断、(2) 公開APIが差分更新非対応で誤送信すると既存設定が消える、(3) 仕様が予告なく変更される |
| 推奨アプローチ | **B（Playwright、人間ログイン済みプロファイル使用）を軸に、下書き保存までを補助自動化。公開ボタンは人間が押す**。Aは認証突破が困難なため非推奨、Cはユーザー環境構築の負担が大きいためPhase2以降の任意オプション |
| 既存実装例 | 個人開発のPlaywright/Selenium/Python直接HTTP実装が複数存在するが、すべて非公式・非保証。npm/PyPI公式パッケージは存在しない |

## 1. 非公式APIエンドポイント一覧

### 1.1 認証系

| 操作 | メソッド・パス | 主要ボディ/パラメータ | 備考 |
|---|---|---|---|
| ログイン | `POST /api/v1/sessions/sign_in` | `{"login": "email", "password": "...", "g_recaptcha_response": "..."}` | **2026-05-21頃よりreCAPTCHA v3トークン必須化**。トークンなしで叩くとHTTP 2xxが返るが`Set-Cookie`ヘッダが付かず、セッションが取れない「無言の失敗」になる |
| セッション確認 | `GET /api/v2/current_user` | - | ログイン状態・ユーザー情報の確認に使用 |

**認証Cookie名**：`_note_session_v5`

### 1.2 記事CRUD系（核心）

| 操作 | メソッド・パス | ボディ/パラメータ | 備考 |
|---|---|---|---|
| 空draft予約作成 | `POST /api/v1/text_notes` | 空ボディでOK | レスポンスに数値`id`とkey（`n`始まり文字列）。この時点ではUI非表示、`status: ""` |
| 下書き保存 | `POST /api/v1/text_notes/draft_save?id={numeric_id}` | `{"name": "タイトル", "body": "<HTML>"}` | `status: "draft"`に昇格。**部分送信可**（差分更新的に振る舞うが、`hashtags`/`magazine_ids`/`circle_permissions`等の公開系メタフィールドはsilentlyに無視され保存されない） |
| 公開・編集 | `PUT /api/v1/text_notes/{numeric_id}` | フルペイロード（下記1.4参照） | **差分更新不可**。draft→publishedもこのエンドポイントで、公開済み記事の編集も同じAPIを使う |
| 記事取得（編集用） | `GET /api/v3/notes/{key}?draft=true&draft_reedit=false` | - | 編集画面と同じ最新差分を取得。公開前に必ずこれで現在値を取得しマージするのが安全 |
| 記事取得（公開情報） | `GET /api/v3/notes/{key}` | - | 通常の記事詳細取得 |
| 下書きに戻す | `POST /api/v2/notes/{key}/change_status` | `{"status": "draft"}` | 有料記事に購入者がいる、メンバーシップ限定、有料マガジン追加済みの場合は**HTTP 403**で拒否 |
| 下書き削除 | `DELETE /api/v1/text_notes/draft_delete?id={numeric_id}` | - | draft状態のみ有効。publishedには使えない |
| 記事削除（公開済み） | `DELETE /api/v1/notes/{numeric_id}` | - | 論理削除（soft delete）。author視点では`status: "deleted"`として残るが、一般ユーザーからは非表示 |
| 記事一覧取得 | `GET /api/v2/notes` | - | - |
| 自分のnote一覧 | `GET /api/v2/note_list/contents?page=1` | - | ダッシュボードが使用 |

### 1.3 画像アップロード系

- ブラウザUI上では「画像を追加」ボタン→ファイル選択→クロップダイアログ→保存、という流れでアップロードが行われる（Playwright実装例より）。
- アップロードされた画像は`free_body`/`pay_body`のHTML中に`<img src=".../img/<image_key>.<ext>">`として挿入され、**`image_keys`配列にそのkeyを出現順で列挙して公開APIに渡す必要がある**（後述1.5の罠を参照）。
- 画像アップロード専用の非公式APIエンドポイントの単体URL・リクエスト構造は、収集した一次資料内では明確なURL（例：`/api/v1/... /image`等）までは特定できなかった。Playwright実装例ではブラウザのファイル選択UIを操作する方式が採られており、**直接HTTPでの画像アップロードAPI呼び出しの詳細は未解明**。この点は本アプリでの実装前に追加のDevTools実機解析が必要。

### 1.4 `PUT /api/v1/text_notes/{id}` フルペイロード構造

| フィールド | 内容 | 省略時の挙動 |
|---|---|---|
| `status` | `"published"`（必須） | 公開されない |
| `name` | タイトル | タイトルが消える |
| `free_body` | 無料部分HTML（各段落は`<p name="UUID" id="UUID">...</p>`形式） | 本文が消える |
| `pay_body` | 有料部分HTML（有料記事のみ） | 有料部分が消える |
| `separator` | 無料部分末尾段落のid（無料/有料の境界） | 分割位置が失われる |
| `price` | 価格（0=無料、100〜50000） | 無料になる |
| `hashtags` | ハッシュタグ配列 | タグが全部消える |
| `magazine_ids` / `magazine_keys` | 追加先マガジン | マガジンから外れる |
| `image_keys` | 本文中で使用した画像keyの配列（出現順） | 画像の整合性検証に失敗し500エラー |
| `slug` | URLスラッグ（**実際のnote_urlには一切影響しない実質廃止フィールド**） | 空文字を送るとURL挙動が壊れる可能性 |
| `body_length` | 可視テキスト長（HTML込みのバイト数ではなく、タグ除去後のUnicodeコードポイント数） | ズレると500エラー |
| `disable_comment` / `is_refund` / `limited` / `index` 等 | 各種フラグ | 設定が既定値に戻る |
| `circle_permissions` | メンバーシップ限定公開設定（空配列=限定なし） | - |
| `lead_form` / `line_add_friend` | 未使用時は`null`ではなく空オブジェクト（`{"is_active": false, ...}`）を送る必要がある | `null`を送るとdeserializeエラーで500 |
| `send_notifications_flag` / `author_ids` / `discount_campaigns` / `pro_coupon_keys` 等 | その他メタデータ | - |

**予約投稿**：`status`を`"published"`＋未来の`publish_at`にすると422エラー。正しくは`status: "reserved"`を送る必要がある（noteのWebエディタの挙動を模倣する必要がある非公開のステータス値）。

### 1.5 公開APIで無応答の500エラーになる代表的な罠

一次資料（実機検証記事）で報告されている、エラーメッセージなしで500が返る4つの原因：

1. `image_keys`を空配列にする（本文中の画像keyを列挙しないと整合性検証で失敗）
2. `lead_form`/`line_add_friend`に`null`を入れる（空オブジェクトが必要）
3. `body_length`にHTML込みの文字数を送る（タグ除去後の文字数が必要）
4. `slug`に空文字を送る

これらはドキュメント化されていない内部検証ロジックであり、**Web版エディタが実際に送信するペイロードをDevToolsで実機キャプチャして突き合わせる**ことが最も確実な解決策とされている。

### 1.6 その他の非公式API（記事投稿には直接関与しないが参考）

| 操作 | メソッド・パス | 備考 |
|---|---|---|
| カテゴリ一覧 | `GET /api/v2/categories` | - |
| カテゴリ別記事一覧 | `GET /api/v1/categories/{key}?note_intro_only=true&sort=new&page=1` | - |
| ハッシュタグ情報 | `GET /api/v2/hashtags/{tag}`（`relatedHashtags`付き）/ `GET /api/v1/hashtags/{tag}`（v1はrelatedHashtagsなし） | - |
| ハッシュタグ別記事一覧 | `GET /api/v3/hashtags/{tag}/notes?order=popular|new|hot&page=N&paid_only=` | - |
| 通知件数 | `GET /api/v3/notice_counts` | - |
| PV統計 | `GET /api/v1/stats/pv?filter=all&page=1&sort=pv` | - |

### 1.7 必要なヘッダー

一次資料の観測によれば：

- `Content-Type: application/json`（JSON POST/PUT時）
- **CSRFトークン**：note.comのHTML内に標準的な`<meta name="csrf-token" content="...">`相当の仕組みがあり、これをJSから読み取って`X-Csrf-Token`ヘッダに設定するのがWebフロントエンドの標準パターン（一般的なRailsアプリのCSRF対策パターンに合致）。ただし2025年4月頃の開発日記記事では「以前はmetaタグから取得できていたが、note.com側でログインページのHTML構造が変わり取得に失敗した」という報告があり、**CSRFトークンの取得元DOM構造は変更が入りやすく、実装前に必ず現行のnote.comのHTMLを直接確認する必要がある**。
- 一部の書込系API（例：v3コメントAPI）では独自の`X-Note-Client-Code`ヘッダが必須という報告があり、**エンドポイントによって必要なカスタムヘッダーが異なる**ため、対象エンドポイントごとに個別確認が必要。
- `Origin`/`Referer`ヘッダも、CSRF/Same-Origin検証の一部として要求される可能性が高い（一般的なRailsアプリのCSRF検証パターン、および収集資料内の観察ツールがこれらのヘッダも記録対象にしている記述から推測）。

## 2. 認証フローの詳細

### 2.1 セッションベース認証の全体像

1. ユーザーが`note.com/login`でメールアドレス（またはnote ID）とパスワードを入力し、ログインボタンを押す。
2. ブラウザは`POST /api/v1/sessions/sign_in`に`{"login": "...", "password": "...", "g_recaptcha_response": "..."}`を送信。
3. 成功時、レスポンスヘッダに`Set-Cookie: _note_session_v5=...`が付与される。
4. 以降のAPIリクエストは、このCookieを付けて送るだけで認証済みとして扱われる（Authorizationヘッダ等の別トークンは不要）。

### 2.2 reCAPTCHA v3による「無言の失敗」（2026年5月以降の破壊的変更）

- 2026年5月下旬（観測ベースでは2026-05-21頃）から、ログインAPIのペイロードに`g_recaptcha_response`（reCAPTCHA v3トークン）が**必須**になった。
- reCAPTCHAトークンなしでこのAPIを叩くと、**HTTPステータスは2xxで返るがSet-Cookieヘッダが付かない**という、エラーとして検知しづらい形の失敗になる。
- reCAPTCHA v3トークンはブラウザ上でGoogle reCAPTCHAスクリプトが生成する動的な値であり、**サーバー側の単純なHTTPリクエストだけで正規のトークンを取得することは実質的に不可能**（reCAPTCHA自体がbot対策として設計されているため）。
- **この変更により、「直接HTTPリクエストでID/パスワードを送ってログインする」方式（アプローチA）は事実上詰んでいる**。既存のPython/Node実装例（`amepress.client.jp`のコード例等）は、Cookie方式に刷新済み、つまり**「一度ブラウザで人間がログインし、発行されたCookie値を環境変数等で外部プログラムに渡す」運用**に移行している（`zenn.dev/centervil`の開発日記でも同様の刷新が報告されている）。

### 2.3 Cookie/セッションの実務上の取得・維持方法

現状確認できる実務パターンは以下の2つ：

1. **Cookie値の手動抽出＋環境変数注入**：ユーザーが通常のブラウザでnoteにログイン後、DevToolsまたはブラウザ拡張で`_note_session_v5`のCookie値を取得し、外部プログラム（Python/Node CLI等）の環境変数・設定ファイルに設定する。以後はそのCookie値をHTTPリクエストに付与して非公式APIを呼ぶ（アプローチAだが、ログイン自体は人間が担当）。
2. **Playwrightの`storageState`（ブラウザプロファイル保存）方式**：Playwrightで一度人間が手動ログインしたブラウザコンテキストの状態（Cookie、localStorage等）をJSONファイル（`storageState`）として保存し、以後の自動実行ではそのファイルを読み込んでログイン済み状態のブラウザコンテキストを再現する（アプローチB、qiita.com/akiraakの実装例で採用）。

### 2.4 セッションの有効期限・維持

- 収集した資料内では、Cookieの明示的な有効期限（Max-Age/Expires）の具体的日数は特定できなかった。ただし複数の実装が「Cookie失効の検知」「CookieExpiredErrorによる例外処理」を組み込んでおり、**セッションは有限期限で失効し、失効時は401が返る**ことが確認できる。
- 実務対応としては、APIレスポンスが401を返した場合に「認証エラー：Cookieを再取得してください」という形でユーザーに再ログインを促すフォールバック処理が必須。

### 2.5 CSRFトークンの取得方法

- Webフロントエンドの標準的な実装は、HTML内の`<meta name="csrf-token" content="...">`相当の要素からJSでトークン文字列を読み取り、書込系リクエストの`X-Csrf-Token`（または類似名）ヘッダに設定するパターン（Rails系アプリの標準CSRF対策）。
- ただし前述の通り、**このmetaタグの存在・取得可否がnote.com側のHTML構造変更によって不安定になった報告がある**（2025年4月時点）。直接HTTPリクエスト方式（アプローチA）を採用する場合、CSRFトークン取得ロジックは他のどの要素よりも壊れやすい部分になる可能性が高い。
- Playwright/Puppeteer方式（アプローチB）であれば、ブラウザが自動的にCSRFトークンをフォーム送信・fetch呼び出しに含めるため、**CSRFトークンの扱いをアプリ側で意識する必要がない**という明確な利点がある。

## 3. 実装アプローチ比較

### 3.1 各アプローチの詳細

#### A. 直接HTTPリクエスト方式（Node.js fetch/axios + Cookie手動管理）

**概要**：ユーザーが手動でnoteにログインし、Cookie値を取得してアプリに設定。以後はNode.js側で`fetch`/`axios`を使い、非公式APIエンドポイントに直接HTTPリクエストを送る。

| 観点 | 評価 |
|---|---|
| メリット | ・ブラウザ起動が不要で軽量・高速 ・サーバーサイド（cron等）での定期実行に向く ・レスポンスJSONを直接扱えるため、下書き保存後のkey取得等のデータ連携が容易 |
| デメリット | ・**reCAPTCHA v3によりプログラムからの直接ログインが不可能**。Cookie値の初回取得は必ず人間のブラウザ操作を経由する必要がある ・CSRFトークンの取得ロジックが不安定（HTML構造変更の影響を受けやすい） ・公開APIがフルペイロード必須で、フィールド欠落によるデータ破壊（本文消失等）のリスクが高い（1.5節参照） ・Cookieの有効期限切れ時に、ユーザーに再度手動でCookie値を取得してもらう運用フローが必要 |
| 実現可能性 | 中（Cookie取得は人間が担当する前提で成立するが、CSRF/500エラーへの対処コストが高い） |
| 難易度 | 中〜高（エンドポイントの罠が多く、実機検証を重ねながらの実装が必要） |
| リスク | 中〜高（フルペイロードの事故で既存記事データを破壊する危険性、CSRF構造変化への追従） |
| 保守性 | 低（DevTools解析を継続的に行い、仕様変更を追従する人的コストが恒常的に発生） |

#### B. Playwright/Puppeteerブラウザ自動化方式

**概要**：ヘッドレス（または有UI）ブラウザを起動し、`storageState`で保存したログイン済みセッションを読み込んで、noteのエディタ画面をUI操作で自動操作する（タイトル入力→本文入力→画像アップロード→タグ設定→公開ボタンクリック）。

| 観点 | 評価 |
|---|---|
| メリット | ・**CSRFトークンやreCAPTCHAをブラウザが自動的に処理するため、認証面の実装負担が最も小さい** ・UI操作を模倣するため、非公式APIのペイロード構造の細部（罠1.5節）を意識する必要がない ・画像アップロードのようなUI依存の複雑な操作（クロップダイアログ等）も自然に扱える ・実際に動作する実装例が複数確認できており、実現可能性の裏付けが強い |
| デメリット | ・noteのUIリニューアルでセレクタが変わると動かなくなる（実際の実装例でも`button[aria-label="画像を追加"]`等の詳細なセレクタに依存し、フォールバック処理が多数必要） ・ブラウザプロセスの起動コストが高く、cron等での高頻度実行には不向き ・`storageState`のCookie有効期限が切れると、ユーザーに再度ログイン操作をしてもらう必要がある ・実行時間が長く（画像アップロード含め数十秒〜数分）、UI操作の待機処理（`waitForSelector`等）のチューニングが必要 |
| 実現可能性 | 高（複数の実装例で実際に投稿成功が確認されている） |
| 難易度 | 中（Playwrightの基本操作は標準的だが、noteエディタ特有のダイアログ・contenteditable操作への対応が必要） |
| リスク | 中（UI変更への追従コストはあるが、データ破壊系の事故は起きにくい。人間の最終確認ステップを挟めば規約リスクも抑制可能） |
| 保守性 | 中（UIセレクタの変更検知・修正が必要だが、非公式APIの内部ペイロード仕様を追うよりは変更頻度・調査コストが低い傾向） |

#### C. ブラウザ拡張/ブックマークレット方式

**概要**：ユーザーのブラウザ上で動作するChrome拡張機能またはブックマークレットとして実装。アプリ側でAI生成した記事データを何らかの形（クリップボード、拡張のストレージAPI経由等）で拡張に渡し、拡張がnoteの投稿フォームにタイトル・本文・タグを自動入力する。公開ボタンは必ず人間が押す。

| 観点 | 評価 |
|---|---|
| メリット | ・**ユーザー自身のログイン済みブラウザセッションをそのまま使うため、Cookie/CSRF/reCAPTCHAの問題が一切発生しない**（人間が普段使っているブラウザの操作を早くするだけ） ・「自分のアカウントの通常操作を効率化する」範囲に収まりやすく、規約リスクが最も低い ・公開ボタンを人間が押す設計を自然に強制できるため、既存設計書の「人間承認フロー必須」方針と最も整合する |
| デメリット | ・Chrome拡張の開発・配布・保守（Chrome Web Store申請、マニフェスト管理等）という新たな開発ラインが必要 ・本アプリ（Webアプリ）から拡張への記事データ受け渡し方法の設計が必要（例：クリップボードコピー→拡張が貼り付け、または拡張がアプリのAPIをポーリング等） ・ユーザーは対象ブラウザに拡張をインストールする追加の手間が必要 ・note側のDOM構造変更で、フォーム自動入力のセレクタが壊れるリスクはPlaywrightと同様に残る |
| 実現可能性 | 高（技術的には確立された手法。既存設計書2.3節で言及の「ブックマークレット＋Cookie抽出」の発展形） |
| 難易度 | 中（Playwrightと同種のDOM操作だが、拡張のライフサイクル管理・Content Script実装の学習コストが加わる） |
| リスク | 低（人間の最終操作が必ず介在するため、規約上の「機械的自動投稿」に該当しにくい） |
| 保守性 | 中（DOM変更対応は必要だが、サーバー側の非公式API変更リスクを負わない） |

### 3.2 比較表（総合）

| 観点 | A. 直接HTTPリクエスト | B. Playwright/Puppeteer | C. ブラウザ拡張/ブックマークレット |
|---|---|---|---|
| 実現可能性 | 中（ログイン突破に人間の介在が必須） | 高（実装例で実証済み） | 高（実装例で実証済み） |
| 難易度 | 中〜高 | 中 | 中（＋拡張開発の学習コスト） |
| 規約リスク | 中〜高（無人化しやすい構造） | 中（無人化も技術的に可能だが人間確認ゲートを設計で強制できる） | 低（人間操作が前提の設計） |
| データ破壊リスク | 高（フルペイロード事故） | 低（UI操作なのでnote側の検証ロジックに従う） | 低（UI操作） |
| 保守コスト | 高（API仕様変更への追従） | 中（UIセレクタ変更への追従） | 中（DOM変更＋拡張配布管理） |
| 認証の複雑さ | 高（reCAPTCHA・CSRF対応が困難） | 低（ブラウザが自動処理） | 最低（ユーザーの既存セッションを利用） |
| サーバー側完全自動実行との相性 | 良い（本来向いている） | 中（ブラウザプロセスが必要だが可能） | 悪い（ユーザーのブラウザ操作が前提） |
| 本アプリの既存方針との整合性 | 低（人間承認ゲートを設計上強制しにくい） | 中〜高（公開ボタン前で止める設計が可能） | 高（人間の最終操作が構造的に必須） |

## 4. 既存のnote自動投稿実装例のまとめ

### 4.1 個人開発のPlaywright実装（Qiita, akiraak氏）

- URL: `qiita.com/akiraak/items/0b7de8642cbf72d81271`
- `storageState`（Cookie等を保存したJSON）を読み込んでログイン済みブラウザコンテキストを復元。
- タイトル欄：`textarea[placeholder*="タイトル"]`に`fill()`。
- 本文欄：`div[contenteditable="true"][role="textbox"]`をクリックし`page.keyboard.type()`でタイピングをシミュレート。
- サムネイル画像：`button[aria-label="画像を追加"]`→ファイル選択（`filechooser`イベント、フォールバックで`input[type="file"]`直接操作）→クロップダイアログの「保存」ボタン。
- 公開フロー：「公開に進む」ボタン→`/publish`ページへの遷移待ち→ハッシュタグ入力（`input[placeholder*="ハッシュタグ"]`）→「投稿する」ボタンクリック。
- 全体を通じて多数の`waitFor`/リトライ/フォールバック処理が必要であり、**UIの複雑さがコード量に直結する**ことが実例から確認できる。

### 4.2 個人開発のSelenium実装（`Shintaisei/note-auto-post`, GitHub, MITライセンス）

- URL: `github.com/Shintaisei/note-auto-post`
- OpenAI GPT-4o + Claude 3.5 Sonnet（フォールバック構成）でAI記事生成・校閲を行い、Selenium WebDriverでログイン・投稿を自動化。
- モジュール構成：`content_generator.py`（AI生成）、`claude_editor.py`/`openai_editor.py`（校閲、フォールバック機能あり）、`note_login.py`/`note_poster.py`（投稿）。
- ログイン情報は`note_login_config.json`にメール/パスワードを平文保存する設計（`.gitignore`で除外指定はあるが、**reCAPTCHA v3必須化以降はこの直接ログイン方式が機能しない可能性が高い**。README作成時点が2026年5月以前と推測される）。
- 「デモモード（投稿なし）」を用意しており、本アプリの`dry_run`的な安全設計思想と共通する。

### 4.3 Python直接HTTPクライアント実装（amepress.client.jp）

- `note_auth_client.py`（Cookie認証クライアント、`CookieExpiredError`例外を持つ）を基盤に、`NoteDraft`（下書き作成）、`NotePublisher`（公開・編集、`fetch→build_payload→update`のマージパターン）を実装。
- **最大の特徴**：公開APIの「差分更新不可・フルペイロード必須」という罠に対し、`fetch()`で現在値を取得し`build_payload()`でマージしてから送信する、という安全策を明確にコード化している。
- `dry_run=True`をデフォルトにし、実際の送信前に内容を表示して確認させる設計（誤公開防止）。
- 有料記事対応、予約投稿、公開直後の本文null現象へのリトライ処理まで実装されている、**収集した資料の中で最も実装が詳細かつ実務的**な例。
- ただし2026年5月のreCAPTCHA v3必須化以降、ログイン部分（`note_auth_client`がどうCookieを得るか）が旧来のID/パスワード直接送信のままだと機能しない可能性が高く、**最新版では人間のブラウザログイン後のCookie値の受け渡しに切り替えている**（`zenn.dev/centervil`の開発日記が示す業界的な移行と整合）。

### 4.4 MCP（Model Context Protocol）サーバー実装

- 先行の設計書（`note-integration-design.md`）で言及されている「MCPサーバーとしてnote運用を自動化する個人開発事例」について、`shimayuz/note-mcp-server`という具体名を再調査したが、**該当リポジトリはGitHub上で404（削除または非公開化）となっており、現時点で内容を直接確認できなかった**。関連する`zenn.dev/centervil`の開発日記では、このリポジトリの実装を参考にCookie認証方式へ刷新したことが述べられており、実在した実装として言及されているが、現物のコード確認はできていない。

### 4.5 npm/PyPI公式・準公式パッケージ

- npm registry・PyPIともに、note.com投稿専用の広く使われている公式・準公式パッケージは確認できなかった（`note-api`、`note-sdk`等の名称で検索したが、無関係な"note"系パッケージ（Notion非公式API、NotebookLM SDK等）がヒットするのみ）。
- 全ての実装例は個人開発のGitHubリポジトリ・note記事上のコードスニペットとして公開されている状態であり、**パッケージ化されて配布されているものは実質存在しない**。

### 4.6 実装例からの総合的な学び

| 学び | 詳細 |
|---|---|
| reCAPTCHA v3への対応 | 直接HTTPログイン方式は2026年5月以降ほぼ機能しない。最新の実装は軒並みCookie/`storageState`方式に移行している |
| フルペイロード事故対策 | 「取得→マージ→送信」パターンの徹底が公開APIの必須プラクティス |
| dry_runの重要性 | 複数の実装が「確認モード」をデフォルトにしており、誤公開防止の設計パターンとして参考になる |
| UI操作の複雑さ | Playwright実装はタイトル・本文だけでも数百行規模になり、画像アップロード・タグ設定を含めるとさらに増大する |
| ヘッダー要件の見落とし | エンドポイントによって独自ヘッダー（`X-Note-Client-Code`等）が必要な場合があり、URL/method/bodyだけでなくヘッダーも含めた実機キャプチャが不可欠 |

## 5. 推奨実装方針と具体的な実装ステップ

先行の設計書（`note-integration-design.md`）の段階的アプローチ（フェーズ1〜5）を維持しつつ、本深掘り調査の結果を踏まえて実装ステップをより具体化する。

### 5.1 推奨方針（変更なし・深掘りにより裏付け強化）

1. **MVP（フェーズ1）**：AI記事生成＋アプリ内プレビュー＋「Markdownをコピー」ボタン。規約リスクゼロ、reCAPTCHA/CSRF/フルペイロード問題を一切回避できる。
2. **フェーズ2（今回の調査で優先度を再評価）**：**Playwrightによる半自動投稿（アプローチB）を、ブラウザ拡張（アプローチC）より先に着手する**ことを推奨する。理由：
   - アプローチCはChrome拡張の新規開発ライン（マニフェスト管理、Web Store申請、Content Script設計）が必要で、本アプリ（Webアプリ）のバックエンド技術スタックから距離がある。
   - アプローチBは既存のNode.js/TypeScriptスタックと同じ言語で実装でき、`storageState`方式によりreCAPTCHA問題を完全に回避できることが実装例で裏付けられた。
   - 「下書き保存まで自動、公開ボタンは人間が押す」設計にすれば、規約リスクをアプローチCと同等程度に抑制できる。
3. **フェーズ3（任意）**：フェーズ2の運用実績を踏まえ、ブラウザ拡張（アプローチC）をユーザー体験向上のオプションとして追加検討。

### 5.2 具体的な実装ステップ（フェーズ2：Playwright半自動投稿）

1. **ログイン状態の受け渡し設計**
   - ユーザーに一度だけ、別ウィンドウ/別タブでnote.comに手動ログインしてもらう。
   - サーバー側でPlaywrightの`chromium.launch({ headless: false または true })`＋`context.storageState()`を使い、ログイン後のCookie等を保存する導線を用意する（例：ユーザー環境でElectron/ローカルヘルパーを使うか、あるいはユーザーがブラウザ拡張的な小さなツールでCookie値を抽出してアプリにアップロードする方式）。
   - **重要**：サーバー側でユーザーのnoteパスワードを保持・送信する設計は絶対に避ける（reCAPTCHA下では機能しない上、規約・セキュリティ上のリスクが大きい）。Cookie/`storageState`のみを扱う。
2. **下書き保存の自動化**
   - `note_articles`テーブルの承認済みレコード（`is_approved = true`）を入力に、Playwrightで`https://editor.note.com/new`を開き、タイトル・本文（Markdown→note用HTML変換が必要）・アイキャッチ画像を自動入力し、「下書き保存」ボタンをクリックする実装を行う（qiita.com/akiraak実装例のロジックを参考に、下書き保存止まりの版を実装）。
   - 各UI要素の待機・クリックには十分なフォールバック処理（複数セレクタ候補、タイムアウト、スクリーンショット保存によるデバッグ容易化）を入れる。
3. **人間の最終確認・公開**
   - 下書き保存完了後、ユーザーに「note側で下書きを確認し、問題なければ手動で公開ボタンを押してください」という通知（アプリ内UIまたはメール等）を出す。
   - 公開操作自体は自動化しない（フェーズ2の範囲では）。これにより「AIは生成・下書きまで、公開の最終判断は常に人間」という既存ガードレール方針を厳格に維持する。
4. **エラーハンドリング・フォールバック**
   - Cookieの期限切れ・UI変更によるセレクタ不一致を検知した場合、明確なエラーメッセージ（例：「note側の画面が変わったため自動入力に失敗しました。手動でコピー＆貼り付けをお願いします」）を出し、フェーズ1の「コピー機能」に自動フォールバックする設計にする。
   - 実行ログ（`note_publish_logs`テーブル、既存設計書7章で言及）に成功/失敗・エラー内容・スクリーンショットパスを記録する。
5. **頻度制限の実装**
   - 1ユーザーあたり1日あたりの自動下書き保存実行回数に上限を設ける（例：数件程度）。これは既存設計書4.1節の方針を維持するもの。

### 5.3 アプローチAを採用しない理由（明確化）

- reCAPTCHA v3必須化により、直接HTTPリクエストでのログインがほぼ不可能。
- Cookie値を人間が手動取得してアプリに渡す運用にしても、CSRFトークンの取得ロジックが不安定（HTML構造変更の影響を受けやすい）で、保守コストがアプローチBより高くなる。
- 公開APIのフルペイロード事故リスク（本文消失等）が、UI操作をそのまま模倣するアプローチBより明確に高い。
- **結論**：直接HTTPリクエスト方式は、記事一覧取得等の読み取り専用の補助機能（例：投稿後のURL確認、統計取得）には使う価値があるが、**投稿・公開という書き込み系の中核機能には採用しない**。

## 6. リスクと制約事項

### 6.1 技術的リスク

| リスク | 詳細 | 対応策 |
|---|---|---|
| reCAPTCHA v3による認証遮断 | プログラムからの直接ログインが不可能（2026年5月以降） | Playwright + `storageState`方式で人間のログインを1回だけ経由する設計に統一 |
| 非公式APIの予告なき変更 | エンドポイントURL・ペイロード構造・必須ヘッダーが無警告で変わる可能性 | UI操作ベース（Playwright）を軸にし、直接API呼び出しは最小限に留める。定期的な動作確認（監視）を運用に組み込む |
| フルペイロード事故 | 公開/編集APIへの部分送信でタイトル・本文・タグ等が意図せず消去される | この操作は直接APIで行わず、UI操作（Playwright）で代替する。直接API利用が避けられない場合は「取得→マージ→送信」を必須プロセス化 |
| DOM構造・セレクタの変更 | noteのUIリニューアルでPlaywrightのセレクタが壊れる | 複数セレクタのフォールバック実装、実行失敗時のスクリーンショット保存、失敗時のフェーズ1（手動コピー）への自動フォールバック |
| Cookieの有効期限切れ | セッションが失効し401エラーになる | 明確なエラー検知とユーザーへの再ログイン依頼フロー |
| 画像アップロードAPIの詳細不明 | 直接HTTP経由の画像アップロードAPIの仕様が本調査では特定できなかった | Playwrightのファイル選択UI操作（`filechooser`イベント/`input[type=file]`）で代替。直接API化する場合は追加のDevTools実機解析が必須 |

### 6.2 規約・運用リスク

| リスク | 詳細 | 対応策 |
|---|---|---|
| 機械的な大量投稿とみなされるリスク | note利用規約の包括条項（スパム・サーバー過負荷・運営が支障と判断する行為の禁止）に抵触する可能性 | 1日あたりの投稿頻度上限、必ず人間が公開ボタンを押す設計、AI生成であることの品質管理（既存ガードレール） |
| 運営による予告なきアカウント制裁 | 非公式API利用・自動化行為に対する運営の裁量判断リスクがゼロにならない | 利用規約変更の定期監視、機能ON時のユーザーへの明示的なリスク説明・同意取得（既存設計書4.1節の方針を維持） |
| パスワードの取り扱い | 直接ログイン方式のように、ユーザーのnoteパスワードをサーバー側で保持する設計は絶対に避けるべき | Cookie/`storageState`のみを扱い、パスワードそのものはアプリ側で一切保存・送信しない設計を必須要件とする |

### 6.3 保守運用上の制約

- 非公式API・DOM構造の解析には継続的な人的コストが発生し、**「動作しない場合がある」ことを前提にした設計**（エラー検知・フォールバック案内・監視）が必須。
- 本調査で参照した一次資料（`note.com/marie_222/n/n6a10366298b0`等）は執筆者個人による実機観測記録であり、**note社が内容を保証したものではない**。実装前には必ず自社での実機DevTools確認を行い、本レポートの内容が現時点でも有効か再検証すること。
- `shimayuz/note-mcp-server`のように、参照されていた実装例が調査時点で既に削除・非公開化されているケースがあり、**個人開発の非公式ツールは継続性が保証されない**前提で参考にとどめるべき。

## 8. 結論

1. **非公式APIエンドポイントの詳細（URL・メソッド・ペイロード構造）は複数の一次資料で高い精度で特定できた**。特に記事CRUD系（`/api/v1/text_notes`系）は最も重要かつ罠が多い領域である。
2. **2026年5月のreCAPTCHA v3必須化により、直接HTTPリクエストでの完全自動ログイン（アプローチA）は事実上不可能**になっており、この制約が実装方針の決定要因として最も重要である。
3. **Playwrightによるブラウザ自動化（アプローチB）が、認証面（reCAPTCHA/CSRF回避）と実装コストのバランスで最も現実的**。既存の実装例（akiraak氏の例）を参考に、本アプリの技術スタック（Node.js/TypeScript）で下書き保存までを自動化し、公開ボタンは人間が押す設計を推奨する。
4. **ブラウザ拡張方式（アプローチC）は規約リスク最小の理想形だが、開発ラインの追加投資が必要**なため、フェーズ2（Playwright）の運用実績を見てから着手するのが合理的。
5. **既存実装例はすべて非公式・個人開発であり、パッケージとして配布されているものはない**。自社実装するか、参考コードとして取り込みつつ自社で保守する前提が必要。
6. **既存設計書（`note-integration-design.md`）の「AIは生成・下書きまで、公開の最終判断は常に人間」という方針は、本深掘り調査によってむしろ技術的合理性でも裏付けられた**（フルペイロード事故・reCAPTCHA制約・規約リスクのいずれも、この方針を採用することでリスクが大きく低減する）。
